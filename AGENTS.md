- Every function, class, and class method must have a standard TSDoc docBlock above the declaration. Types in `*.types.ts` and schemas in `*.schemas.ts` do not require TSDoc.
- For a single-line comment, use `// ...` rather than `/** ... */`. Reserve `/** ... */` for TSDoc on functions, classes, and methods (multi-line blocks with `@param`, `@returns`, and related tags when applicable).
- In function and method bodies, put a blank line between logical steps: after initial `const`/`let` setup, after guard branches that early-return or throw, before shared setup used by later branches, and before a final fallback `return`.
- Name interfaces with an `I` prefix (for example `ICapabilities`). Name domain type aliases with a `Type` suffix (for example `AddToolInputType`). Conventional JSON and scalar aliases such as `JsonValue`, `JsonObject`, `JsonArray`, and `JsonPrimitive` keep their established names.
- Keep `src/core/` framework-only and application-agnostic. No file under `src/core/` (specs included) may directly import application-owned modules: `src/resources/**`, `src/tools/**`, `src/services/**`, `src/capabilities/**`, `src/providers.ts`, or `src/config.ts`. `src/core/core-boundary.spec.ts` enforces this direct-import boundary; do not add indirect dependencies on those application modules either. If adding, replacing, or deleting an application capability, service, or configuration value requires editing `src/core/`, stop: that belongs in core only as an intentional framework behavior change, never as an application tweak.
- Core specs must use local test-only fixtures or mocks instead of the sample capabilities, services, or server config. `src/core/core-boundary.spec.ts` enforces the direct-import boundary. Put application-level integration tests outside `src/core/` (for example `src/capabilities/capabilities.spec.ts`); core tests verify framework behavior with local fixtures, while application specs exercise the real sample capabilities end-to-end.
